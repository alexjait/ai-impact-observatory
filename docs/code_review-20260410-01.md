# Code Review — AI Impact Observatory (Backend + Frontend-Web)

> Revisión profunda de seguridad, calidad de código y UX/UI.
> Fecha: Abril 2026.

---

## Resumen ejecutivo

El proyecto está bien concebido y bien estructurado para un MVP. La separación de responsabilidades es clara, el modelo de datos es coherente con los requerimientos, y hay decisiones de diseño maduras (sesiones en DB, tokens hasheados, Turnstile en formularios sensibles, ValidationPipe con whitelist). Sin embargo, hay **issues de seguridad reales** que deben corregirse antes de salida a producción, y hay algunos patrones de código que conviene mejorar.

## 1. Vulnerabilidades de Seguridad

### 🔴 CRÍTICO — Credenciales reales hardcodeadas en `.env` commiteado

El archivo `backend/.env` está en el repositorio con **secretos reales**:

[Valores de credenciales eliminados. Rotar los secretos afectados.]

**Impacto**: Cualquiera con acceso al repo tiene las claves de Google OAuth, Resend y Turnstile. Si el repo es o fue alguna vez público, esas claves están comprometidas.

**Acción**: 
1. Rotar **todas** esas claves inmediatamente en Google Cloud Console, Resend y Cloudflare.
2. Añadir `.env` al `.gitignore` y nunca commitear el archivo real (solo `.env.example` sin valores).
3. Verificar en el historial de git si el archivo fue commiteado antes y purgar si es necesario (`git filter-repo`).

El `.env.example` ya existe y tiene los placeholders correctos. El problema es el `.env` real commiteado.

### 🔴 CRÍTICO — Contact form sin rate limiting ni Turnstile

El endpoint `POST /api/v1/contact/messages` acepta mensajes anónimos sin ningún captcha ni rate limit.

```typescript
// contact.controller.ts
@Post('messages')
async createMessage(@Body() dto: CreateContactMessageDto, @Req() request: Request) {
  return this.contactService.createMessage(
    await this.resolveAuthenticatedUserId(request),
    dto,
  );
}
```

**Impacto**: El endpoint es trivialmente abusable para spam masivo y para llenar la DB de mensajes maliciosos. También puede ser usado para enumeración: si hay validación de email, un atacante puede descubrir qué emails están registrados.

**Acción**: Agregar Turnstile al formulario de contacto, o al menos un rate limiting por IP a nivel de middleware/NestJS.

### 🟠 ALTO — `X-Forwarded-For` confiado sin validación de proxy

```typescript
// auth.controller.ts
private getRequestIp(request: Request): string | undefined {
  const forwardedFor = request.headers['x-forwarded-for'];
  if (typeof forwardedFor === 'string') {
    return forwardedFor.split(',')[0]?.trim() || undefined;
  }
  // ...
}
```

El header `X-Forwarded-For` puede ser manipulado libremente por cualquier cliente. Si no hay un proxy de confianza delante del servidor que sobreescriba este header, un atacante puede falsear su IP para evadir la validación de Turnstile que asocia IP al token.

**Acción**: Si se despliega detrás de un proxy conocido (Nginx, Cloudflare), configurar `trust proxy` en Express y usar `request.ip` directamente, que ya está resuelto por el proxy. Si no hay proxy, ignorar `X-Forwarded-For`.

### 🟠 ALTO — `displayName` sin límite de longitud máxima en backend

```typescript
// register.dto.ts
@IsString()
@MinLength(2)
displayName!: string;
```

No hay `@MaxLength`. Un atacante puede registrarse con un displayName de megabytes, causando DoS en la DB o en cualquier renderización del string.

**Acción**: Agregar `@MaxLength(100)` (o el límite razonable del dominio).

---

### 🟠 ALTO — `returnTo` en login potencialmente expone open redirect parcial

```typescript
// auth.service.ts
private resolveReturnTo(returnTo?: string | null): string {
  if (!returnTo) return env.appBaseUrl;
  if (returnTo.startsWith('/')) return this.buildAppUrl(returnTo);
  if (returnTo.startsWith(env.appBaseUrl)) return returnTo;
  return env.appBaseUrl;
}
```

La lógica es mayormente correcta salvo un edge case: si `appBaseUrl` es `https://myapp.com`, una URL como `https://myapp.com.evil.com/x` pasaría el `.startsWith()` check.

**Acción**: Parsear la URL con `new URL(returnTo)` y verificar que `origin === new URL(env.appBaseUrl).origin`.

### 🟡 MEDIO — Compiled `.js` files en el repositorio

Hay archivos `.js` compilados en `src/` conviviendo con los `.ts` fuentes:

```
src/app.module.js  ← compilado
src/app.module.ts  ← fuente
src/main.js        ← compilado
src/main.ts        ← fuente
...
```

Esto es un problem porque:
1. Genera confusión: ¿qué archivo es la "verdad"?
2. Los `.js` compilados podrían divergir de los `.ts` si alguien edita el `.ts` pero no recompila.
3. Si un sistema de CI/CD o Docker ejecuta los`.js` directamente, podría correr código stale.

**Acción**: Agregar `src/**/*.js` al `.gitignore` del backend. El build debe producir artefactos en `dist/`.

---

### 🟡 MEDIO — Sin rate limiting en endpoints de autenticación

Aunque Turnstile protege los formularios, los endpoints de auth no tienen rate limiting a nivel de servidor. Un atacante podría:
- Hacer muchas solicitudes de `forgot-password` con diferentes emails para confirmar cuáles existen.
- Aunque la respuesta siempre es `{ accepted: true }`, el timing de la respuesta podría revelar si el email existe.

El `forgot-password` tiene protección parcial (retorna `{ accepted: true }` siempre), pero el timing diffiere porque cuando el usuario existe se hace más trabajo.

**Acción**: Implementar `@nestjs/throttler` para los endpoints de auth, especialmente login, forgot-password y register.

---

### 🟡 MEDIO — Sin Content Security Policy (CSP)

El backend no configura headers de seguridad HTTP (CSP, HSTS, X-Frame-Options, etc.).

**Acción**: Instalar `helmet` de NestJS/Express y configurar CSP apropiado para el portal público.

```typescript
// main.ts
import helmet from 'helmet';
app.use(helmet());
```

---

### 🟡 MEDIO — Token de reset de contraseña sin `@MaxLength` en DTO

```typescript
// reset-password.dto.ts
@IsString()
token!: string;
```

El `token` no tiene validación de longitud. Un adversario podría enviar un token arbitrariamente largo, causando carga innecesaria en la operación de hash.

**Acción**: Agregar `@MaxLength(128)` al campo `token` (los tokens son 64 chars hex).

---

### 🟢 BIEN — Aspectos de seguridad correctamente implementados

Estos puntos están bien hechos y vale la pena reconocerlos:

- ✅ **Tokens hasheados en DB**: Sessions, password reset tokens y flow states guardan `SHA-256(token)`, nunca el token en claro.
- ✅ **Bcrypt con 12 rounds**: Costo razonable para producción.
- ✅ **HttpOnly cookies**: Las cookies de sesión no son accesibles por JS.
- ✅ **`sameSite: 'lax'`**: Protección CSRF básica para navegación normal.
- ✅ **Turnstile en register/login/forgot-password/reset-password**: Bot protection en los flows de mayor riesgo.
- ✅ **`whitelist: true, forbidNonWhitelisted: true`** en ValidationPipe: Previene property injection.
- ✅ **Email normalizado a lowercase**: Previene duplicados y case confusion.
- ✅ **Tokens de un solo uso**: `consumeAuthFlowState` marca el token como `usedAt`.
- ✅ **Invalidación de sesiones al resetear password**: `session.deleteMany({ where: { userId } })`.
- ✅ **CORS con origins explícitos**: No `*`.
- ✅ **`escapeHtml` en emails**: Previene XSS en contenido de emails HTML.

## 2. Calidad de código

### ✅ Lo que está muy bien

**Arquitectura modular clara**: La separación en módulos NestJS (`auth`, `public`, `contributions`, `moderation`, `editorial`, `admin`, `contact`) es coherente y sigue Single Responsibility. Cada módulo tiene su controller, service y DTOs propios.

**DTOs bien tipados**: Los DTOs usan `class-validator` correctamente con decoradores específicos. El `RegisterDto` valida complejidad de contraseña con regex, `@IsEmail()`, `@IsBoolean()` para términos, etc.

**Manejo de transacciones correcto**: Los flows críticos como `register` usan `prisma.$transaction` para garantizar atomicidad (crear user + identity + flow state juntos).

**Rollback ante fallo de email**: Si el email de verificación falla al enviarse, se elimina el usuario recién creado:
```typescript
} catch (error) {
  await this.prisma.user.delete({ where: { id: created.user.id } });
  throw error;
}
```
Esto es buena práctica para no dejar usuarios sin poder verificar su cuenta.

**Frontend como Server Components**: El uso de Next.js con Server Components para las páginas que no necesitan interactividad es correcto. Los fetch de datos ocurren en el servidor, el cliente recibe HTML renderizado.

**Lib de API bien organizada**: `api.ts` concentra todos los tipos y funciones de acceso al backend, lo que facilita el mantenimiento.

**`resolveAuthenticatedUserId`** en public controller: Permite personalizar respuestas para usuarios autenticados (ej: `isFollowing`) sin requerir autenticación, elegante.

### ⚠️ Mejoras recomendadas de código

**1. `ensureDefaultRoles` se llama en cada register y Google login**

```typescript
async register(dto: RegisterDto): Promise<...> {
  await this.ensureDefaultRoles(); // ← DB upsert en cada registro
```

Esto hace N upserts de roles en cada registro de usuario. Debería ejecutarse una sola vez en el arranque (OnModuleInit) o en la migración. En producción con muchos registros simultáneos, genera contención en la tabla `roles`.

**2. Idempotency key en email de verificación basada en userId**

```typescript
{ idempotencyKey: `verify-email/${input.userId}` }
```

Esto es bueno para Resend, pero significa que si el usuario pide reenvío de verificación no se puede generar un nuevo email (Resend lo ignoraría silenciosamente). Considera incluir el `tokenId` del flow state en la key.

**3. El frontend hace doble fetch de `getSessionUser` en algunas páginas**

El `SiteShell` ya hace `getSessionUser()` internamente, pero la página `page.tsx` también lo llama:
```typescript
// page.tsx
const [activityResponse, methodology, user] = await Promise.all([
  getActivities({ locale, pageSize: 6 }),
  getMethodology(locale),
  getSessionUser(),  // ← llamado también en SiteShell
]);
```

Esto resulta en dos requests HTTP al backend por carga de página. En Next.js 15 los Server Components no comparten automáticamente el cache entre llamadas a la misma URL. Considera usar React `cache()` para deduplicar dentro del mismo request.

**4. Ausencia de tests**

No se encontró ningún archivo de test (`*.spec.ts`, `*.test.ts`). Dado que la lógica de negocio es compleja (flujos de auth con múltiples estados, flujos editoriales con auditoría), la ausencia de tests es un riesgo significativo ante refactors.

**5. `BackofficeShell` hace fetch de session adicional innecesario**

El componente `backoffice-shell.tsx` recibe `user` como prop pero la página padre ya lo obtuvo. Verificar que no haya fetches adicionales dentro.

**6. Falta tip de tipo para `authMethods` en `AuthenticatedUser`**

```typescript
// api.ts (frontend)
authMethods: string[];  // ← debería ser ("local" | "google")[]
```

El tipo `string[]` no aprovecha el discriminated union. Esto puede causar errores sutiles en la UI si se compara contra valores específicos.

**7. `fetchJson` pierde el status code en errores**

```typescript
throw new Error(`Request failed for ${path} with status ${response.status}`);
```

Para poder distinguir 401 (no auth) de 403 (no permission) de 500 (error) en el frontend, conviene crear un error tipado que incluya el status code. Actualmente todas las respuestas no-ok con `allowFailure: false` generan el mismo tipo de error genérico.

## 3. Look & Feel / UX

### ✅ Fortalezas visuales

**Paleta de colores cohesiva y premium**: El warm beige (`#f5f0e8`) con el teal oscuro (`#1f5f5b`) como accent crea una combinación editorial sofisticada, coherente con el tono de "observatorio curado". No es una paleta genérica.

**Tipografía excelente**: La combinación de Manrope (UI, labels, botones) con Newsreader (headings editoriales) da exactamente la sensación de publicación seria con buena legibilidad. El `letter-spacing: -0.03em` en headings es correcto para ese tamaño.

**Glassmorphism bien aplicado**: El uso de `backdrop-filter: blur` en header y footer, y `rgba` en cards, es elegante y no abusado. El header sticky con blur es correcto.

**Jerarquía visual clara**: El eyebrow + h1 + p es un patrón consistente en todas las páginas. Los `status-pill`, `tag-chip`, `activity-card__granularity` son tokens diferenciados visualmente.

**Diseño del backoffice coherente con el portal**: Mismo sistema de diseño para ambos, lo que es la decisión correcta para un MVP con equipo pequeño.

---

### ⚠️ Problemas de UX a corregir

**1. No hay menú mobile / hamburger**

El header (`site-header__inner`) usa `display: flex` con todos los elementos en línea pero no hay ningún breakpoint con menú mobile. En pantallas chicas, el header colapsa el contenido. Para un portal público en 2026, el responsive es obligatorio desde el día 1.

**2. La homepage no tiene meta tags dinámicos por locale**

```typescript
// layout.tsx
export const metadata: Metadata = {
  title: "AI Impact Observatory",
  description: "Editorial observatory for tracking AI impact on human activities.",
};
```

Es metadata estática en inglés. Para soporte SEO multiidioma real, cada página debería generar `metadata` con el locale correcto, incluyendo `<html lang>` dinámico y `hreflang` links. El `<html lang="en">` está hardcodeado.

**3. El `buildPath` usa query params para el locale, no segmentos de URL**

```typescript
// site.ts
export function buildPath(path: string, locale: Locale, ...): string {
  params.set("locale", locale);
  return `${path}?${query}`;
}
```

Todas las URLs son `/activities?locale=es` en vez de `/es/activities`. Esto es un anti-patrón para SEO multiidioma. Google trata `?locale=es` como un parámetro de filtro, no como una variante idiomática. El brief menciona "SEO multiidioma con rutas separadas por locale como recomendación inicial", y la implementación actual diverge de eso aunque no es requisito cerrado.

**4. Sin feedback de loading en el frontend**

Los Server Components de Next.js renderizan sincrónicamente, lo que significa que si el backend tarda, el usuario ve una página en blanco durante la carga. No hay `loading.tsx` ni skeleton states. Para una experiencia premium, se espera algún tipo de indicación.

**5. La `activity-card` trunca el texto a 4 líneas con `-webkit-line-clamp`**

Esto está bien visualmente, pero solo funciona en navegadores modernos. El fallback para navegadores sin soporte es simplemente texto sin truncar. Menor issue pero vale la pena documentarlo.

**6. El `empty-panel` de homepage está hardcodeado como mensaje de desarrollo**

```tsx
<p className="section-copy">
  {localized(locale, {
    en: "The public APIs are already live. As we keep publishing reviewed seed items, they will start to appear here.",
    es: "Las APIs públicas ya están funcionando..."
  })}
</p>
```

Este copy de "las APIs ya están funcionando" es jerga de desarrollo, no copia para el usuario final. Antes de lanzar al público debería ser reemplazado por algo como "El catálogo se está completando, volvé pronto."

**7. Sin confirmación antes de acciones destructivas en backoffice**

En el backoffice, acciones como reset del seed no tienen modales de confirmación (al menos no visibles en el frontend). Para un sistema editorial, esto es un riesgo UX importante.

**8. El `lang` del HTML es estático**

```tsx
// layout.tsx
<html lang="en" ...>
```

Siempre renderiza `lang="en"` independientemente del locale del usuario, lo que rompe la accesibilidad (lectores de pantalla usarán pronunciación inglesa para contenido en español) y el SEO.
